# MCP Trading Simulator

A paper-trading application that connects AI agents to account tools, market quotes, web research and persistent memory through the Model Context Protocol. A FastAPI service and TypeScript dashboard show four simulated portfolios, transactions and agent activity.

**A runnable no-key demo is included.** It uses deterministic fixture orders and prices, not AI decisions. The application does not connect to a brokerage or place real orders.

## Project goal

The goal is to demonstrate how an AI application can discover tools, read structured context, perform validated actions and expose the results for inspection through MCP. Paper trading gives the project a concrete workflow: read an account, look up a price, record a simulated order, and inspect the updated balance and holdings.

The intended outcome is a reproducible engineering demonstration of **agent–tool integration, state management and observability**. Trading profitability is not the success criterion. Success means tool calls work, invalid orders are rejected, account calculations remain consistent, and the dashboard accurately reflects stored activity.

## What happens in the demo?

The no-key demo follows this sequence:

1. Create four simulated accounts, each with **$10,000 of virtual cash**.
2. Use fixed example prices and scripted buy/sell orders to populate the accounts.
3. Save balances, holdings, transaction rationales and valuation snapshots in SQLite.
4. Serve those records through FastAPI and display them in the dashboard.

`examples.offline_demo` calls the Python account methods directly. It does **not** invoke an AI model or MCP. The separate `examples.mcp_roundtrip` demonstrates the real MCP connection using a local server: discover tools, buy two fixture shares, read the account resource, and verify that a negative quantity is rejected.

The optional agent runner adds model-driven decisions and research to this workflow. That path is implemented but has not been validated through a paid end-to-end run. The current dashboard demo is scripted, even if a model name appears in a configuration or label.

## Where do the numbers come from?

**The no-key dashboard uses created demo data, not prices scraped from a website.** Ticker symbols are familiar examples; their fixture prices are deliberately fixed and do not represent current market quotes.

| Demo account | Example ticker | Fixed price | Scripted actions | Remaining shares |
| --- | --- | ---: | --- | ---: |
| Value | AAPL | $100.00 | Buy 10, sell 1 | 9 |
| Macro | MSFT | $200.00 | Buy 5, sell 1 | 4 |
| Balanced | SPY | $400.00 | Buy 4, sell 1 | 3 |
| Innovation | NVDA | $50.00 | Buy 20, sell 1 | 19 |

The account logic applies a **0.2% simulated spread** on each side: purchases cost slightly more than the quoted price, and sales receive slightly less. This explains the small negative demo returns. There are no real charges or transfers.

For example, the Value account buys 10 AAPL shares at $100.20 and sells one at $99.80. It then has $9,097.80 in cash and nine shares valued at $900, giving a total portfolio value of **$9,997.80** and a simulated P&L of **−$2.20**. The dashboard may round these amounts for display.

| Quote mode | Data source | External market-data request? |
| --- | --- | --- |
| `fixture` | Fixed prices shown above; used by the no-key demo | No |
| `simulated` | Synthetic prices generated from the ticker and time | No |
| `live` | Previous closing prices from Massive, explicitly configured with a key | Yes |

All three modes use simulated accounts. Even `live` changes only the quote source; it does not connect a brokerage or place real trades.

## What does the data look like?

An account contains virtual cash, a strategy, holdings, transactions and valuation history. This shortened example shows the Value account after its scripted orders; omitted transaction timestamps and snapshot times are generated when the demo runs.

```json
{
  "name": "value",
  "balance": 9097.8,
  "net_deposits": 0.0,
  "holdings": {"AAPL": 9},
  "transactions": [
    {"symbol": "AAPL", "quantity": 10, "price": 100.2,
     "rationale": "Deterministic fixture demo; no model decision"},
    {"symbol": "AAPL", "quantity": -1, "price": 99.8,
     "rationale": "Exercise the simulated sell path"}
  ],
  "total_portfolio_value": 9997.8,
  "total_profit_loss": -2.2
}
```

Positive transaction quantities represent purchases; negative quantities record completed sales. Order inputs themselves must always use positive quantities. Portfolio value is cash plus the current value of holdings. P&L subtracts the initial virtual capital and net deposits, so adding cash is not counted as profit.

- **`artifacts/accounts.db`:** an `accounts` table stores account JSON, while a `logs` table records timestamps, event types and messages.
- **`artifacts/demo_report.json`:** a readable snapshot generated by the no-key demo.
- **Dashboard API:** exposes balances, positions, trades, valuation history and recent logs; it uses a slightly different response shape from the account report above.

These generated files are ignored by Git. The repository contains code that recreates the example data, rather than a downloaded financial dataset. Demo charts show snapshots from the scripted run; they are not historical stock-price charts.

## How MCP is used

**Model Context Protocol (MCP)** provides a common interface for a client to discover available tools, call them with structured arguments, and read resources from a server. Here, local servers run as separate Python processes and communicate over standard input/output (`stdio`).

| MCP component | Role in this project |
| --- | --- |
| Accounts tools | Read cash and holdings, validate simulated buy/sell orders, and update strategies |
| Account resources | Read structured account snapshots and strategy text through `accounts://...` resource URIs |
| Market tool | Return a quote from the selected fixture, synthetic or previous-close source |
| Research tools | Fetch pages, optionally search with Tavily, and retain context through a memory server |
| Summary tool | Record activity locally; external notification delivery is optional and disabled by default |

For a tool call, the client sends the tool name and arguments, the server executes the corresponding Python function, and the result returns to the client. In the agent workflow, the model selects those calls. In the protocol test, Python selects them deterministically so the integration can be tested without model credentials.

MCP does not create market data or make investment decisions on its own. It connects the application to the code and context that perform those jobs. The dashboard reads FastAPI endpoints rather than communicating with MCP directly.

## What it demonstrates

- Custom MCP tools for balances, holdings, simulated orders and strategy updates.
- MCP resources for account snapshots and strategies, exposed over stdio.
- A researcher agent exposed as a tool, with fetch, optional Tavily search and per-persona memory.
- Four strategy personas coordinated in bounded parallel agent rounds.
- SQLite persistence and activity logs, consumed by a FastAPI/TypeScript dashboard.
- Input validation, explicit quote-source modes, tested P&L accounting and five solution notebooks.

## Quick start: no API keys

Requires Python 3.12+ and uv. The MCP dependency is constrained to v1 because this project uses `mcp.server.fastmcp`.

```bash
uv sync
uv run python -m examples.offline_demo
uv run python -m examples.mcp_roundtrip
MARKET_MODE=fixture uv run uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

The demo creates four paper accounts under ignored `artifacts/`. A second run refuses to overwrite existing demo accounts unless `--reset` is supplied. The MCP roundtrip uses temporary storage and starts a real local MCP server.

For the dashboard, use Node.js 20+ and npm in a second terminal:

```bash
cd frontend
npm ci
npm run dev
```

Open **http://localhost:5174**. Keep `MARKET_MODE=fixture` on the API when reviewing fixture data. The frontend uses a local API proxy on port 8000. A compiled frontend alone needs an equivalent `/api` reverse proxy when deployed.

## Optional agent run

```bash
uv sync --extra agents
cp .env.example .env
# Set OPENAI_API_KEY and a TRADER_MODEL available in your account.
# Optionally set TAVILY_API_KEY for search.
uv run python -m backend.reset --confirm
uv run python -m backend.trading_floor --rounds 1
```

The reset command replaces the four simulation accounts. Agent runs use external model APIs and can incur charges. Node/npx and uvx are needed for research MCP servers. External notifications are disabled by default; summaries go to the local log. Provider-specific credentials are required only when selecting that provider.

`MARKET_MODE=simulated` uses synthetic time-varying quotes. `fixture` uses fixed test quotes. `live` requires `uv sync --extra live-market` and a Massive key and uses previous closing prices, not real-time execution prices. All modes retain paper-only accounts. Live quote failures do not silently switch to synthetic data.

## Architecture and limitations

```text
Agent runner → Trader agents → Accounts MCP → SQLite
                      ├──────→ Market MCP → fixtures / synthetic / prior close
                      ├──────→ Summary MCP → local log (optional notification)
                      └──────→ Researcher tool → Fetch / Search / Memory MCP
SQLite → FastAPI → TypeScript dashboard
```

This is a local prototype. One worker owns each persona; account updates are not safe for concurrent writers to the same account. MCP resources are not authenticated tenant boundaries. Dashboard metrics from the fixture demo are synthetic examples, not investment results. Live model behavior and optional third-party integrations need their own end-to-end validation.
